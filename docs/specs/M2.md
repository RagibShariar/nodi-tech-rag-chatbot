# M2: Vector search (embeddings + Qdrant)

Status: APPROVED (2026-11-12). Installs, dependencies and collection rebuild approved.
Open questions decided: run the baseline retrieval check now, comparing three embedding models.

## Goal

Turn every chunk into an **embedding** (a list of numbers that represents its meaning), store them in
**Qdrant**, and for a question return the **top 5 most similar chunks** with scores and sources.

Also measure a **baseline retrieval hit rate** on the eval questions, so M3 (hybrid search) has a
"before" number to beat.

M2 does no BM25, no reranking, no LLM answers.

## Inputs / outputs

- **Input:** the 50 chunks from M1 (re-generated in-process from `data/`, so they are never stale).
- **Output 1:** a Qdrant collection `chunks_<model>` with 50 points. Each point holds one vector plus a
  payload: all chunk fields (`chunk_id`, `source`, `section`, `status`, `content`, ...) and `tokens`.
- **Output 2:** `search(question, k=5)` returns a list of hits: `score`, `chunk_id`, `source`, `section`, `content`.
- **Output 3:** baseline hit@5 numbers in `docs/experiments.md`.

## Design

### 1. Embeddings via Ollama's REST API

`POST http://localhost:11434/api/embed` with `{"model": "bge-m3", "input": "<text>"}` returns
`{"embeddings": [[...1024 floats...]], "prompt_eval_count": <tokens>}`.

- Called with `httpx` (a plain HTTP client), so the code shows that embedding is just a REST call.
- One text per call. 50 chunks on CPU take a few seconds, so batching isn't worth the extra code yet.
- `prompt_eval_count` gives the **real token count** per chunk (promised in M1). We print min/max/avg
  and compare max to bge-m3's 8192 limit.
- **What gets embedded:** chunk `embed_text` (context line + content). Questions are embedded as-is.
- **Model-specific prefixes:** `nomic-embed-text` expects `search_document: ` before documents and
  `search_query: ` before questions. `qwen3-embedding` expects an instruction before questions
  (`Instruct: <task>\nQuery: <question>`) and nothing before documents. bge-m3 needs none.
  Stored per model in one small dict.
- **Embedding model ≠ chat model.** We do not embed with the Qwen *chat* LLM: chat models are trained to
  predict the next word, not to place similar meanings close together. Qwen3-Embedding is Qwen's
  separate model trained for that job.

### 2. Qdrant in local (embedded) mode, no server

`QdrantClient(path="artifacts/qdrant")` runs Qdrant **inside our Python process** and saves to a folder,
like SQLite vs a Postgres server. Same client API as a real server: switching later means setting
`QDRANT_URL` in `.env`, with no code change.

- Why: no Docker on this machine; installing Docker Desktop (WSL2, admin) is heavy for 50 vectors.
- Trade-offs: one process at a time (the folder is locked), no web dashboard, and exact (brute-force)
  search instead of an HNSW index. With 50 vectors, exact search is instant and slightly *more* accurate.
- **Distance:** cosine.
- **Point IDs:** Qdrant needs an integer or UUID, so `uuid5(chunk_id)`. It is deterministic: same chunk,
  same ID.
- **One collection per model** (`chunks_bge-m3`, `chunks_nomic-embed-text`) because vector sizes
  differ (1024 vs 768).
- **Rebuild:** `index` drops and recreates its own collection each run, so deleted or renamed chunks
  never linger. ⚠️ **Approving this spec = permission for `index` to drop/recreate only the
  `chunks_<model>` collections in `artifacts/qdrant/`.** That data is derived and rebuilds in seconds.
  Nothing else is ever deleted.

### 3. Config: `.env`

`src/config.py` reads `.env` (via `python-dotenv`), with defaults so it works without one:

```
OLLAMA_URL=http://localhost:11434
EMBED_MODEL=bge-m3
QDRANT_PATH=artifacts/qdrant
# QDRANT_URL=http://localhost:6333   # optional: use a Qdrant server instead of local mode
```

`.env.example` is committed; `.env` is not (already in `.gitignore`).

### 4. Testable without Ollama

`build_index()` and `search()` take an `embed` function as a parameter (dependency injection).
Unit tests pass a **fake embedder** and an **in-memory Qdrant** (`QdrantClient(":memory:")`), so they run
in milliseconds with no model. A few **integration tests** call the real Ollama and are **skipped** if
Ollama isn't running.

## Baseline retrieval check (`scripts/retrieval_check.py`)

- Questions: all eval questions whose `source_documents` is not `none` (36 of 40).
- **hit@5** = at least one expected source document appears among the top-5 chunks' sources.
- Report: overall hit@5, hit@5 per question `type`, and the list of misses (question + what came back).
- Run for **bge-m3**, **nomic-embed-text** and **qwen3-embedding:0.6b**; record all three in
  `docs/experiments.md`. The model with the best hit@5 becomes the default (ties: bge-m3, the planned choice).
- Not the full M6 eval: no LLM, no answer grading. It only measures retrieval.
- **Expectation, stated honestly in advance:** pure vector search will likely miss some `exact_id`
  questions (`ND-1042`, `SEC-EXC`). That is the known trap M3 fixes. We record the real number either way.

## Tests

**Unit (fake embedder, in-memory Qdrant):**
1. Indexing 50 chunks creates 50 points; payload contains `chunk_id`, `source`, `content`, `status`, `tokens`.
2. Point IDs are deterministic (`uuid5(chunk_id)`); indexing twice still gives 50 points, not 100.
3. Rebuild removes stale points (index 3 chunks, then 2, and the collection has 2).
4. `search` returns at most `k` hits, sorted by score descending.
5. Collection name depends on model (`chunks_bge-m3`).
6. Prefixes: nomic gets `search_query: ` / `search_document: `, qwen3-embedding gets an instruction
   on queries only, bge-m3 gets none.

**Integration (real Ollama, skipped if not running):**
7. bge-m3 returns a 1024-dim vector and a positive token count.
8. Same text gives the same vector (deterministic).
9. Similarity makes sense: "How many days of annual leave do I get?" is closer to the handbook leave
   chunk than to the printer notice.
