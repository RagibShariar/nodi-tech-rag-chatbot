# M3: Hybrid search (BM25 + vector, fused with RRF) + reranking

Status: APPROVED (2026-11-12). Dependencies and model download approved.
Open questions decided: keep the reranker even if it doesn't help, default mode chosen by score
(latency breaks ties); 20 candidates, then measure latency.

## Goal

Add **keyword (lexical) search** next to vector search, merge both result lists with **Reciprocal Rank
Fusion (RRF)**, then **rerank** the merged candidates with a cross-encoder and keep the top 5.

Measure every stage separately so we know what each one adds (the score decides).

M3 does no LLM answers (that's M4).

## Pipeline

```
                 ┌─ vector search (bge-m3 + Qdrant, from M2) → top 20 ─┐
question ────────┤                                                     ├─ RRF (k=60) → top 20 ─ reranker → top 5
                 └─ BM25 keyword search (rank_bm25)        → top 20 ─┘                       (bge-reranker-v2-m3)
```

Four **modes**, so each stage can be measured on its own:

| Mode | What runs |
|---|---|
| `vector` | M2 baseline: vector top 5 |
| `bm25` | BM25 top 5 |
| `hybrid` | vector + BM25 → RRF → top 5 (no reranker) |
| `rerank` | vector + BM25 → RRF → top 20 → reranker → top 5 (full pipeline) |

## Design

### 1. BM25 keyword search (`src/retrieval/bm25.py`)

- `rank_bm25.BM25Okapi`, built **in memory** from the 50 chunks at startup (takes milliseconds; no
  persistence needed).
- Indexes the same `embed_text` as vector search (context line + content), so file and section names count.
- **Tokenizer** (where BM25 succeeds or fails):
  - lowercase;
  - keep hyphenated codes whole **and** their parts: `ND-1042` → `nd-1042`, `nd`, `1042`;
    `X-Nodi-Key` → `x-nodi-key`, `x`, `nodi`, `key`. So "ND-1042", "nd 1042" and "error 1042" all match;
  - **Bangla:** Python's `\w` does not match Bangla vowel signs (e.g. `া`, `ি`), so `\w+` would chop Bangla
    words into fragments. The pattern explicitly includes the Bangla Unicode block (U+0980–U+09FF);
  - no stemming, no stopword list: BM25's IDF already gives common words like "what" a low weight.
    Revisit only if the numbers show a need.

### 2. Reciprocal Rank Fusion (`src/retrieval/fusion.py`)

`rrf_score(chunk) = Σ over lists  1 / (60 + rank_in_that_list)`

- Uses **ranks, not raw scores**: BM25 scores (0 to ~20) and cosine scores (0–1) are on different scales
  and can't be added directly.
- A chunk found by only one method still gets a score, so vector-only finds (cross-language) survive.
- `k = 60` is the standard value from the original RRF paper (Cormack et al., 2009).
- Ties broken by chunk ID, so the order is deterministic.

### 3. Reranker (`src/retrieval/rerank.py`)

- **Cross-encoder** `BAAI/bge-reranker-v2-m3` (multilingual, 568M params), via `sentence-transformers`
  `CrossEncoder`, CPU.
- It reads **(question, chunk) together** and outputs one relevance score, so it is more accurate than
  embeddings (which encode question and chunk separately), but much slower. That's why it only sees the
  top 20 candidates, never all 50.
- Model downloaded once from Hugging Face (~2.3 GB) into the user's HF cache, not the repo.
- Injectable like the embedder: tests use a fake reranker.

### 4. Pipeline (`src/retrieval/pipeline.py`)

`retrieve(question, mode="rerank", k=5) -> list[Retrieved]`, where each result keeps a **debug trail**:
vector rank, BM25 rank, RRF score, rerank score. The `search` CLI gets `--mode` and prints that trail,
so we can see *why* a chunk ended up where it did.

Settings in `.env` / `src/config.py`: `RERANK_MODEL`, `CANDIDATES=20`, `RRF_K=60`.

## Dependencies (need approval)

| Package | Why | Size |
|---|---|---|
| `rank_bm25` | Standard BM25 implementation, pure Python | tiny (+ numpy) |
| `sentence-transformers` | Runs the cross-encoder reranker | pulls in **PyTorch (CPU)** + `transformers`: a few hundred MB |
| model `BAAI/bge-reranker-v2-m3` | The reranker named in CLAUDE.md | ~2.3 GB download (disk: 103 GB free) |

**Honest note:** in M2 I rejected `sentence-transformers` to avoid PyTorch. That reason was valid for
embeddings, because Ollama does them. It doesn't hold for reranking: I checked, and Ollama 0.40.16 has no
rerank endpoint (`/api/rerank` and `/v1/rerank` both return 404). So PyTorch is now justified.

**Rejected alternatives:**
- Postgres full-text search for BM25: no Postgres here, a server for 50 chunks, and `ts_rank` isn't BM25.
- Qwen LLM as reranker (ask it to score each chunk): 20 LLM calls per question on CPU is far too slow.
- Smaller rerankers: `bge-reranker-base` has no Bangla; `jina-reranker-v2-base-multilingual` has a
  non-commercial license.

## Expected risks (stated before measuring)

- **The reranker might not help here.** With hit@5 at 100% and MRR at 0.935, there's little room. If it
  doesn't improve MRR/all@5, we report that honestly and choose the default mode by the numbers.
- **Latency:** query embedding (~2–3s) + reranking 20 pairs with a 568M model on a 4-core CPU could add
  several seconds per question. Measured, not guessed. If too slow, fewer candidates (e.g. 10).
- **BM25 can't do cross-language** (an English question has no words in common with the Bangla doc).
  RRF should keep the vector-side result. We'll check Q34 specifically.
