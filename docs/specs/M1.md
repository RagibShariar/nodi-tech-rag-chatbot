# M1: Ingestion (parse + chunk)

Status: APPROVED (2026-11-12). Dependencies `pdfplumber` and `pytest` approved.
Open questions decided: keep FAQ as one chunk, do not merge tiny sections. Revisit after the M6 eval.

## Goal

Turn the 12 files in `data/` into a list of **chunks**: small, self-contained pieces of text that later
milestones will embed (M2) and search (M3). Each chunk keeps enough metadata to cite its source.

M1 does no embedding, search or LLM calls. It only parses, chunks, prints and saves.

## Inputs

- `data/*.md`: 11 markdown files (one is Bangla, one is superseded, one contains a prompt injection)
- `data/expense_reimbursement_policy.pdf`: 1 page, with a 5-row table whose cells wrap over several lines

## Outputs

1. A list of `Chunk` objects in memory (used by M2 and M3)
2. `artifacts/chunks.jsonl`: one chunk per line (generated, gitignored)
3. A readable printout of every chunk in the terminal, so we can check them by eye

### Chunk shape

| Field | Example | Why |
|---|---|---|
| `chunk_id` | `employee_handbook_v3.md#4` | Stable, unique ID (filename + position) |
| `source` | `employee_handbook_v3.md` | Used for `[source]` citations and eval hit rate |
| `doc_title` | `Nodi Tech Ltd. — Employee Handbook` | From the `#` H1 line |
| `section` | `3. Leave > Carry forward` | Heading path (breadcrumb) |
| `status` | `current` or `superseded` | `superseded` if the filename contains `SUPERSEDED` |
| `content` | the raw section text | Shown to the LLM and to the user |
| `embed_text` | context line + `content` | What M2 will embed and M3 will index with BM25 |

**Context line** (deterministic, no LLM):
`[Source: <source> | <doc_title> | Section: <section>]`, plus ` | Status: SUPERSEDED` for the old policy.
This puts the document and section name into every chunk. Without it, a chunk like
"Up to 5 unused days can be carried forward..." does not say whose rule it is or that it is about leave.

## Design

### Step 1: Parse each file to markdown text

- **Markdown files:** read as-is with `encoding="utf-8"` (the Windows default encoding would corrupt Bangla).
- **PDF:** use `pdfplumber` to convert the PDF into the same markdown format:
  - Title line becomes `# ...`. Numbered headings (`1. How to claim`) become `## ...`.
  - The table is pulled out with pdfplumber's table extractor (not plain text extraction), turned into a
    markdown table and placed where it appeared. Cells that wrap over two lines are joined with a space
    (`Local transport (ride-share,` + `CNG)` becomes `Local transport (ride-share, CNG)`).
  - The text inside the table area is not extracted a second time, so the table doesn't appear twice.

After this step every document is markdown, so a single chunker handles all 12 files.

### Step 2: Chunk by structure (headings)

- Split on `##` and `###` headings. Each section is one chunk, with `section` = heading path.
- Text between the `#` title and the first `##` (version line, intro, the pricing table) is its own chunk,
  with `section` = `(intro)`. If it is empty, no chunk is made.
- Files with no `##` headings (FAQ, error codes, vendor notice) become one chunk each.
- **Size limit:** `MAX_CHARS = 1500`. If a section is longer, split it at paragraph boundaries (blank lines).
- **Tables are never split from their header.** If a table alone is longer than `MAX_CHARS`, split it by
  rows and **repeat the header row** in every piece.

With the current data, no section exceeds 1500 chars, so we expect about 50 chunks and no splitting.
The splitting rules are still built and tested with synthetic input, because they define how the chunker
behaves on larger documents.

### What M1 does NOT do

- No cleaning of the prompt injection in `vendor_notice_printer.md`. It is ingested as normal data.
  Defending against it is M5's job (fencing chunks in the prompt). Removing it here would hide the problem.
- No handling of superseded content beyond the `status` field. Preferring current docs is M4/M5's job.
- No real token counting. We print character counts. Real token counts come in M2 with the bge-m3 tokenizer.
- No code-block handling in markdown (there are no code blocks in `data/`).

## Tests (pytest)

1. **All files loaded:** 12 distinct `source` values, each with ≥ 1 chunk.
2. **PDF table intact:** one chunk contains the header `Expense type | Limit | Notes` **and** the row
   `Hotel outside Dhaka | BDT 6,000 per night | Pre-approval from team lead required`.
3. **Wrapped cells joined:** `Local transport (ride-share, CNG)` appears as one cell.
4. **No duplicate PDF table text:** `Hotel outside Dhaka` appears in exactly one PDF chunk.
5. **Markdown table header kept:** the chunk containing `ND-1042` also contains `| Code | HTTP status |`.
6. **Large table split repeats header** (synthetic 100-row table): every piece starts with the header row
   and is ≤ `MAX_CHARS`.
7. **Long section split** (synthetic text): pieces are ≤ `MAX_CHARS` and break at blank lines.
8. **Heading path:** the handbook chunk containing `31 March` has section `3. Leave > Carry forward`.
9. **Bangla preserved:** a chunk from `office_transport_canteen_bn.md` contains `৮:১৫`.
10. **Exact codes preserved:** `ND-1042` and `SEC-EXC` appear verbatim in chunk content.
11. **Status:** all chunks from the SUPERSEDED file have `status == "superseded"`, all others `"current"`.
12. **Context line:** every `embed_text` starts with `[Source: <source>`.
13. **Deterministic:** chunking twice gives identical `chunk_id`s and content.
14. **Eval coverage:** every filename in `eval_questions.csv` (except `none`) is a chunk `source`.

## How we check by eye

Run `python -m src.ingest.run` and check:
- the PDF table reads correctly row by row,
- no chunk starts in the middle of a sentence,
- tiny chunks (e.g. handbook `6. Contact`) still make sense on their own,
- the Bangla text prints correctly in the terminal.

## Open questions for you

1. **FAQ as one chunk:** the FAQ has 6 Q&A pairs and no headings, so it becomes one chunk covering 6 topics.
   That can weaken retrieval, because one embedding has to represent all 6 topics. Option: split on
   `**question**` lines. My suggestion: keep it as one chunk for now and let the M6 eval decide.
2. **Tiny chunks:** sections like `6. Contact` are one line. Should small sections be merged with their
   neighbours? My suggestion: no, keep one section per chunk for now. The context line gives them meaning.
