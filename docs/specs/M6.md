# M6: Evaluation (all 40 questions, retrieval + answer correctness)

Status: DONE 2026-11-13 (human grading skipped by decision; see Decisions)

## Goal

One script that runs all 40 questions in `eval/eval_questions.csv` through the **full chatbot** (the same
engine the web page uses) and reports, against the targets in CLAUDE.md:

| Metric | Target |
|---|---|
| Retrieval: correct source document in the top 5 (in-scope questions) | ≥ 90% |
| Answers: correct vs `expected_answer` | ≥ 85% |
| Guardrails: Q35–Q37 out-of-scope + Q38–Q40 guardrail handled | 6/6 |
| Version conflict: annual leave is 18, never 15 (Q29; also Q30 carry-forward 5, not 10) | ✅ |

Plus: citation rate, results per question type, latency, and **how much we can trust the judge**.

## The hard part: who decides if an answer is "correct"?

M4/M5 used substring checks and they were wrong several times ("31 March" vs "March 31st"; a forbidden
phrase inside a correct refusal). For 40 varied questions we need a judge that understands meaning:

### LLM-as-judge

A second LLM call per answer: give the model the question, the expected answer and the bot's answer, and a
strict rubric:

- **CORRECT**: every key fact of the expected answer is present (any wording), nothing contradicts it, no
  invented facts. For behaviour questions (e.g. "should say it does not know"), the behaviour matches.
- **PARTIAL**: right direction, but a key fact is missing (e.g. K3's "80 taka" missing).
- **INCORRECT**: wrong, contradicts the expected answer, invents facts, or wrong behaviour.

Output: JSON `{"verdict": ..., "reason": ...}`, temperature 0. **Only CORRECT counts toward the 85% target**;
PARTIAL is reported separately.

The bot's answer is **fenced** in the judge prompt too: an answer could contain injected text (e.g. quoting
the vendor note), and the judge must treat it as data.

### Its known limits (what M6 must measure, not assume)

- **Self-grading bias:** judging qwen3.5:4b's answers with qwen3.5:4b. A model tends to like its own style.
- **Small-model reliability:** a 4B judge can misread, be too lenient, or be fooled by confident wording.
- **Verbosity bias:** long answers can look "more correct".
- **Cost:** one more LLM call per answer (~15s on the office PC CPU).

So we validate the judge two ways:

1. **Judge sanity set** (`scripts/judge_sanity.json`, written and frozen before use): ~8 hand-made
   (question, expected, answer) triples with a known verdict: exact correct answer, a correct paraphrase,
   "15 days" for Q29, a missing key fact, a confident made-up answer, an empty answer, an answer to a
   different question, a correct refusal. The judge must get them right.
2. **Human agreement:** the judge's 40 verdicts vs **your** (Ragib's) grades on the same 40 answers.
   Report agreement % and where they disagree. If agreement is poor, the human grade is the official score
   and the judge is reported as unreliable. **That comparison is the M6 lesson on LLM-as-judge limits.**

## Design

### `scripts/run_eval.py`

- Each question in a **fresh session** (no history), default retrieval mode (rerank), as in the web app.
- Per question it records: answer, retrieved sources, retrieval hit (doc-level, top 5), all expected sources
  found, cites a retrieved file, timing, judge verdict + reason.
- Version-conflict check for Q29/Q30 (18 not 15; 5 not 10), using the M4 "only if marked outdated" rule.
- `--seeds 42 1 2`: run the whole set per seed and report **mean and per-question consistency**
  (correct in 3/3, 2/3, ...), because one seed is not proof (K3 was 2/5 in M5).
- `--rejudge FILE`: re-judge saved answers **without regenerating them**, so a judge change doesn't need a
  50-minute rerun, and answers and judge stay separate.
- Saves `artifacts/eval_seed<N>.json`; prints a report.
- Writes `artifacts/eval_for_review.csv` (id, question, expected, answer, empty `human` column) for human
  grading. The judge's verdict is **left out** so the human grade isn't anchored by it; the comparison is
  done afterwards by the script.

### `src/eval/judge.py`

Judge prompt, fenced inputs, JSON parsing with a safe fallback (unparseable → `ERROR`, counted separately,
never silently as correct). Uses the same `OllamaChat` client.

### Human labels

Your grades are saved in `docs/eval/human_labels.csv` (committed: they are evaluation data, like the
frozen guardrail set).

## Files

```

tests/eval/test_judge.py, tests/scripts/test_run_eval.py
```

No new dependencies. No new models (judge = qwen3.5:4b unless the data says otherwise; see open question 3).

## Runtime

Office PC (CPU): ~55s per answer + ~15s per judge call ≈ **~47 minutes per seed** for 40 questions. Three
seeds ≈ 2.5 hours, run in the background. Re-judging saved answers ≈ 10 minutes.

Home laptop (i5-12500H, RTX 3050 Laptop GPU; Ollama on GPU, reranker on CPU): not measured yet. Expected
faster; the first run records real per-answer and per-judge timings. Timings from the two machines are
reported separately, never compared as the same setup.

4. Version-conflict check for Q29/Q30.
